# Spec: remote-exec

## Requirements

1. The skill executes commands on remote machines over SSH, using `~/.ssh/config` directly; it never manages connection settings and only refers to host aliases.
2. Every remote execution is preceded by a security review performed by an independent `remote-exec-reviewer` subagent, which inspects the verbatim remote command text, including any script body.
3. The reviewer returns one of three classifications: `safe` (execute immediately), `risky` (the caller must obtain an explicit user confirmation first), `deny` (refuse; no confirmation unlocks it).
4. Ambiguous commands are classified `risky`, never `safe`.
5. Classification follows what a command does, not which binary it names: the read-only forms of commands that can also write (`ip addr show`, `timedatectl status`, `dpkg -l`, `crontab -l`, `docker compose ps`, `kubectl rollout status`, …) are safe. The recognised forms are a whitelist shared by the reviewer and the hook; an unrecognised subcommand, flag or extra argument is not a read-only form and keeps the risky classification.
6. Built-in principles: remote read-only operations are safe; copying data from the remote machine to the local one is safe; writes confined to `/tmp` or `/var/tmp` are safe; writes outside temp directories are risky; changes to system, kernel, network, service, application, runtime or other machine configuration are risky; destructive operations are denied.
7. The policy is extensible: users declare additional `allow` / `review` / `deny` rules in `~/.claude/remote-exec/rules.toml`, evaluated together with the built-in principles. A user `allow` rule can clear a built-in risky classification but never a built-in deny.
8. A deterministic `PreToolUse` hook enforces the gate at the tool layer: it blocks a remote command with no review verdict attached, independently re-derives the verdict for commands marked `safe`, blocks every deny-tier command regardless of markers, and blocks `ssh <host>` with no command.
9. An unreadable or invalid rule file denies every remote command; the policy layer never fails open.
10. `~/.ssh` is not readable by the agent: the guard hook denies any shell command that touches the ssh config directory (config, keys, known_hosts - read, list or copy), Claude's `permissions.deny` blocks its Read/Edit/Write tools on the same paths, and the global prompt states the rule. A host alias is used exactly as the user gave it; a failure to resolve or connect is reported verbatim instead of being diagnosed from the config.
11. Claude Code and every configured Codex profile get a real reviewer subagent and the same hook, verified active on each (see Codex hook trust in Design).

## Design

- **Verdict marker.** The reviewer's verdict travels to the hook as an inert environment prefix on the command: `REMOTE_EXEC_REVIEW=safe` (reviewer said safe) or `REMOTE_EXEC_REVIEW=approved` (reviewer said risky and the user confirmed). ssh does not forward the variable, so it has no effect on the remote side.
- **Single policy source.** `skills/remote-exec/references/policy.md` holds the evaluation order, the safe / risky / deny tables and the rule-file schema. The reviewer reads it at review time; `hooks/remote-exec-guard.py` implements the same tiers in code.
- **Evaluation order** (identical in both): built-in deny → user `deny` → user `review` → user `allow` → built-in defaults → `[defaults].ambiguous` (`review` unless set to `deny`). First match within a tier wins, so rule order in the file is priority.
- **Read-only forms.** `READ_ONLY_FORMS` in the hook maps a gated command name to a regex that must match its *whole* argument string, so `ip addr show` is recognised while `ip addr add …` is not. It is applied per shell segment (`read_only_form`); verified segments are blanked out of the text before the write / config / fetch tables run, with the delimiters kept so `curl … | sh` stays one pipeline. If nothing is left, the command is safe; otherwise the remaining segments are judged as before, and each one's leading command must be read-only for the fallback to call the command safe. Whitelist semantics: an unknown subcommand, flag or extra argument simply does not match, so the classification is unchanged from before. Deliberately excluded: dry-run flags, `docker exec` / `kubectl exec`, and cache-writing queries.
- **The ssh directory is off-limits.** `SSH_DIR` in the hook matches `~/.ssh`, `$HOME/.ssh`, `${HOME}/.ssh`, `/home/<user>/.ssh` and `/root/.ssh` against the heredoc-stripped command, and denies outright - before any remote-invocation parsing, so it covers `cat`, `ls`, `grep`, `cp` alike. `ssh -G <alias>` needs no new rule: a command-less ssh was already blocked. Claude's tool side is covered by `permissions.deny` in `~/.claude/settings.json`; Codex has no read-tool permission list, so there the hook is the only deterministic layer.
- **Temp-write allowance.** A write-category match is safe only when every absolute path in the command text sits under `/tmp` or `/var/tmp`. A write with no absolute path is risky, since the target depends on the remote working directory.
- **Transfer direction.** For `scp`/`sftp`/`rsync`, the remote spec's position decides: remote source and local destination is a download (safe); a remote destination is an upload (risky). `--rsync-path` / `--remote-option` / `-M` make a download risky, because they run a command on the remote side.
- **Command extraction.** The hook tokenizes the Bash command with `shlex` so quoted payloads stay intact, splits on shell operators, skips environment assignments and wrappers (`env`, `timeout`, `nice`, … including their own arguments), recurses into interpreter payloads (`bash -c '…'`) up to depth 3, and parses ssh option/host/command layout to isolate the remote text. Each invocation in a chain is judged separately with its own marker.
- **Cross-agent enforcement.** Codex implements Claude-Code-compatible hooks: same `PreToolUse` event, same snake_case stdin payload, same `hookSpecificOutput.permissionDecision` contract. One script serves both, registered in `~/.claude/settings.json` (`hooks.PreToolUse`) and in each profile's `$CODEX_HOME/hooks.json` (`{"hooks":{"PreToolUse":[...]}}`), with `[features].hooks = true` in the Codex config (the older `codex_hooks` name is deprecated).
- **Codex hook trust.** Codex loads a hook but skips it silently while its trust status is `untrusted` - the state of any freshly written `hooks.json`, and a failure mode that looks like a correct config whose hook never runs. Trust is persisted in `config.toml` as `[hooks.state."<source path>:pre_tool_use:<group>:<index>"]` with `enabled = true` and `trusted_hash = "sha256:..."`. Neither value is guessable, so `scripts/codex-trust-hook.py` asks Codex over the app-server `hooks/list` RPC, writes the entry, and re-queries to confirm `trusted`. The installer runs it per profile and warns if the hook did not end up active. The hash covers the handler command line, not the script body, so policy edits do not need re-trusting.
- **Multiple Codex profiles.** `--codex-home PATH` is repeatable on installer and uninstaller. Profiles may share one `config.toml` (on this machine `~/.codex-midas`, `~/.codex-seb` and `~/.codex` resolve to the same file, and `skills/` is shared too) while `hooks.json` and the trust key stay per profile, so each profile is registered and trusted separately and the trust entries coexist in the shared file. Config edits are in-place writes, never renames, so symlinks and hardlinks survive.
- **Second Codex layer.** `$CODEX_HOME/rules/remote-exec.rules` (execpolicy) resolves every `ssh`, `scp`, `sftp`, `rsync` and `ansible` invocation to `prompt`. Coarser than the hook, but it also covers `ansible`, which the hook does not inspect.
- **Heredoc bodies are data, except when they are the remote command.** The hook lifts heredoc bodies out before analysis, so text that merely mentions a remote command (documentation, a Python string) is not misread as an invocation. The one shape where the body *is* the remote command is `ssh host bash -s <<'EOF' … EOF`, the normal way to send more than a one-liner: there `stdin_script` substitutes the body for the unreadable `bash -s` text and the tables judge it line by line, so a read-only script runs on a `safe` verdict instead of prompting every time. Conditions, all of them necessary for the reviewed text to be the text that runs: the marker is **quoted** (an unquoted `<<EOF` is expanded by the *local* shell before it is sent, so its body is not kept at all), the shell is one of `bash`/`sh`/`dash`/`ksh`/`zsh` with short flags only (`-c` takes its script from an argument, so the heredoc is data there), and the body is a heredoc rather than a pipe or a `<` redirect (which the hook cannot see). A body naming `~/.ssh` is not promoted, keeping the verdict it had before. Comment lines are dropped, and `set` / `cd` / `export` / `exit` count as read-only, since a script body routinely opens with them; control flow the tables cannot read still falls to the ambiguous tier. The reviewer subagent follows the same rule, so both halves agree.
- **Bounded loops and conditionals are judged on their body.** `effective_command` looks past the keywords of a construct that runs its body a bounded number of times (`do done if then elif else fi case esac { } !`) and past a `for VAR in <list>` header, so the segment is judged on the command it actually runs; `read_only_form` skips the same keywords, so `do ip addr show` is still recognised as a query form. The iteration list is dropped only from that check and stays in the text the write, config and path tables scan - which is what keeps it sound: `for d in /tmp/a /tmp/b` is a temp write, `for d in /tmp/a /etc/nginx` is a write to /etc/nginx, `for d in $DIRS` is a write with no absolute path. **`while` and `until` are deliberately not transparent**, and a `for` loop containing the background operator is risky by an explicit rule: the tables classify *what* runs and have no concept of *how often*, so `while true; do curl … & done` would otherwise read as "read-only command" while being a fork bomb. `BACKGROUND` excludes `&&` and descriptor dups (`2>&1`). A C-style `for ((…))` and `case` (its selector and `)` pattern labels are not commands) remain risky - conservative, not a claim that they are dangerous.
- **Tool-name independence.** The hook keys off the presence of `tool_input.command` rather than a tool name, and accepts the argv-list form (`["zsh","-lc","…"]`), because Codex shell tool names differ per build. The Codex registration deliberately omits `matcher` for the same reason.
- **Shared rule file.** Both agents read `~/.claude/remote-exec/rules.toml`; `REMOTE_EXEC_RULES` overrides the path and is what the test suite uses.
- **Installation.** `install.sh [--claude] [--codex]` symlinks the skill, installs the reviewer definition and the hook, merges the hook registration additively (existing hooks on the same matcher are preserved, config backed up as `.remote-exec.bak`), and copies the rule template only when no rule file exists. `uninstall.sh` reverses all of it and keeps the rule file.

## Trust model

The hook is a slip-catcher, not a sandbox. It cannot prove a reviewer ran; that rests on the skill contract, the same model as `privileged-exec`. "The hook did not block it" is never approval. This is stated in both READMEs and in the policy reference.

## Verification

- `remote-exec/tests/test_hook.sh` - built-in policy and marker semantics: unreviewed commands blocked; safe verdict honoured only for genuinely safe commands; approved risky commands run; deny-tier blocked even when approved; download safe vs upload risky; wrappers, chains and nested shells cannot hide an invocation; local commands untouched; the read-only forms of mutation-capable commands run without a prompt while their mutating forms still require one. Also: every shape of access to `~/.ssh` is denied (`cat`, `ls`, `grep`, `cp`, `ssh -F`), while `/etc/ssh/sshd_config`, `grep -rn ssh .` and heredoc text mentioning the path are not.
- `remote-exec/tests/test_rules.sh` - user rules: each tier overriding the built-in defaults, host globs, `ambiguous = "deny"`, `allow` unable to unlock a deny, and broken / invalid rule files denying rather than failing open.
- `remote-exec/tests/test_codex_rules.sh` - `codex execpolicy check` expectations for the Codex rules file; skipped when `codex` is absent.
- Codex hook activation is verified by the installer: `hooks/list` must report the guard as `trusted` in that profile, otherwise the install warns.
- Installer verified against a sandboxed `HOME`: registration merge preserves the pre-existing `intranet-guard.sh` entry, re-running is idempotent, uninstall removes only our entry and keeps `rules.toml`.
- Live, Claude Code: an unreviewed remote read issued from a session was denied by the hook with the review instructions.
- Live, Codex (both profiles): with trust recorded the hook runs under `codex exec`, and a probe handler returning `deny` produced `hook: PreToolUse Blocked` with the command not executed; a read-only remote read was allowed once marked safe. Each profile's installed hook copy was also checked directly against the marker/verdict matrix.
